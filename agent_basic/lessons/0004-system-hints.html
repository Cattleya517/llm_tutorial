第 4 課 · System hint：每一輪臨時貼上的狀態欄

agent_basic 讀書會 · 約 12 分鐘 · 對照函式：SystemHintConfig、_get_system_hint、_get_system_state、_get_timestamp、_get_detailed_error，以及 execute_task 裡的 messages_to_send、tool_call_counts、metadata_parts

這一課的收穫：讀完後你能說出四種 hint 各自「貼在哪裡」——時間戳貼在 user 訊息前綴、系統狀態貼在歷史複本末尾、工具計數貼在 tool 結果前綴、詳細錯誤貼在 tool 結果內容——並且解釋為什麼狀態欄只貼在複本上、不存進歷史。

動機：長任務裡模型會忘記「現在幾點、做到哪」

第 3 課說過，模型每一輪看到的世界就是 conversation_history。任務一長，這份歷史裡堆滿了工具輸出，模型很容易搞不清楚現在幾點、自己在哪個目錄、同一個指令已經重跑了幾次。原書 README 把解法叫做「Agent 狀態欄」（system hint）：由程式根據真實執行狀態生成一段短摘要，在送給模型之前，用一條 role: "user" 訊息接在 context 末尾[1]。

關鍵是「程式生成」這四個字。模型自己寫的計畫可能是錯的、過時的；狀態欄是從 os.getcwd()、datetime.now()、計數器直接讀出來的事實。它適合提醒時間、進度、約束，但不能取代工具結果。

四種 hint，四個貼的位置

agent.py 的「hint」其實不是一個東西，是四個小機制，貼在訊息的不同位置。這是本課最重要的一張表：

Hint產生它的函式貼在哪裡存進歷史？
時間戳_get_timestamp（約 204 行）[2026-10-19 14:03:11] 前綴：貼在 user 任務前面（execute_task 開頭，約 807 行），也貼在每條 tool 結果前面（約 940 行）。系統狀態的 Current Time: 也用它是
系統狀態_get_system_state（約 180 行）→ _get_system_hint（約 270 行）一條新的 role: "user" 訊息，接在歷史複本的末尾（約 828–831 行）。內容：現在時間、cwd、OS、shell、Python 版本否

時間戳與工具計數：為什麼要「存」

這兩個是事件發生當下的事實：「這條結果是幾點拿到的」「這是第幾次叫這個工具」。它們是工具結果的一部分，存進歷史才合理——模型下一輪往回看時，才能看出「我剛剛已經 ls 了四次」。system prompt（_init_system_prompt）明講：Notice tool call numbers … if you see high numbers, change strategy。注意 tool_call_counts 只在 reset() 歸零，REPL 模式下跨任務累計。

詳細錯誤：把 exception 翻譯給模型

在 _execute_tool 的 except 分支，exception 不會直接丟出去，而是交給 _get_detailed_error：組出 Tool 'read_file' failed with FileNotFoundError: …、呼叫參數、（verbose 時）traceback，再由 _get_error_suggestions 依錯誤類型附上建議，例如 Verify the file/directory path exists | Check the current working directory。整段字串塞進 {"error": …}，走跟正常結果一模一樣的路回到模型手上。模型看到的是「怎麼修」，不只是「壞了」。

關鍵機制：複本上貼，歷史不留

在 VSCode ⌘F 搜 messages_to_send。execute_task 的 while 迴圈裡，每一輪問模型之前只有這五行：

messages_to_send = self.conversation_history.copy()   # 1. 淺複本
system_hint = self._get_system_hint()                  # 2. 現在的狀態欄（可能是 None）
if system_hint:
    messages_to_send.append({"role": "user", "content": system_hint})   # 3. 只接在複本上
self.last_llm_messages = messages_to_send              # 4. 留一份給 trajectory.json

response = self.client.chat.completions.create(model=self.model, messages=messages_to_send, ...)

所以狀態欄每一輪都送（模型永遠看得到），但從不 append 到 self.conversation_history。下一輪再重新 .copy()、重新生成、重新接上。三個理由：

  1. 會過期。cwd 會因為 cd 改變、時間一直走、TODO 狀態一直變。存進歷史的舊狀態欄只會跟新的打架。
  2. 會膨脹。20 輪就是 20 份一模一樣的「System: Darwin … Python 3.12」，純粹浪費 token。
  3. 它是狀態欄，不是對話。打個比方：遊戲畫面上的 HUD 每一幀重畫，不會存進劇情；原書就叫它 Agent 狀態欄。

對照 _get_system_hint（約 270 行）：只有 enable_system_state 和 enable_todo_list 兩個開關決定它回不回 None；內容就是 === SYSTEM STATE === 加上（有 TODO 時）=== CURRENT TASKS ===。

為什麼接在末尾、不是改 system prompt？歷史前段不動，provider 的 prompt cache 才打得到；而最新的狀態放在最接近模型「要回答」的位置，最不會被忽略。這跟 Anthropic 講的 context engineering 一致：每一輪送進去的應該是「the smallest set of high-signal tokens」[2]——狀態欄小、訊號高、不重複。

SystemHintConfig：每種 hint 一個開關

往上翻到 class SystemHintConfig（約 83 行），五個布林值對應五種機制：

class SystemHintConfig(BaseModel):
    enable_timestamps: bool = True        # [time] 前綴
    enable_tool_counter: bool = True      # [Tool call #n for 'x']
    enable_todo_list: bool = True         # 狀態欄裡的 === CURRENT TASKS ===
    enable_detailed_errors: bool = True   # 關掉就只回 str(e)，沒有建議
    enable_system_state: bool = True      # 狀態欄裡的 === SYSTEM STATE ===

要做對照實驗，建構時傳一個 config 進去即可：

agent = SystemHintAgent(config=SystemHintConfig(enable_system_state=False))

此時若 TODO 清單還是空的，_get_system_hint 回 None，送出模型的那一刻 last_llm_messages 跟 conversation_history 會長得一模一樣（trajectory.json 裡的後者會再多最後一條 assistant 回覆）——這是確認「hint 真的只是臨時貼上」最直接的證據。

TODO 清單也搭這班車

模型用 rewrite_todo_list 建的清單，工具結果只回 {"success": true, "total_items": 3} 這種計數；清單本身是透過 === CURRENT TASKS === 每一輪在狀態欄裡重新出現——這正是 Anthropic 文中「structured note-taking」的一種實作，第 5 課細講。

這些可以先跳過

  • simulate_time_delay、simulated_time、_advance_simulated_time：書裡 demo「多天任務」用的假時鐘，預設關閉。
  • timestamp_format：只是 strftime 格式字串。
  • _get_system_state 裡的 Windows / Darwin / Linux 分支：只是決定 Shell Environment: 那行怎麼寫。
  • _get_detailed_error 裡 if self.verbose: 的 traceback：給人看的，模型通常用不到。

預測一下

選一個答案，立刻看解釋。目的是檢查你有沒有分清楚「貼在複本」與「存進歷史」，不是考試。

一個任務跑了 8 輪結束。之後在 agent.conversation_history 裡搜 === SYSTEM STATE ===，會找到幾條？

狀態欄只 append 到 messages_to_send（conversation_history.copy() 的複本），從不 append 回 self.conversation_history。每一輪都是現做現貼、用完即丟。想看證據，比對 trajectory.json 的 last_llm_messages 與 conversation_history。

模型第 5 次呼叫 read_file。它是從哪裡看到「這已經是第 5 次」？

tool_call_counts['read_file'] 變成 5，metadata_parts 把 [Tool call #5 for 'read_file'] 拼在 tool 結果 content 的第一行，然後整條 role: "tool" 存進歷史。狀態欄（_get_system_hint）裡沒有計數；system prompt 只有「看到大數字要換策略」這條規則，數字本身在工具結果裡。

模型用 rewrite_todo_list 建了三項 TODO。之後每一輪，它在哪裡看到這份清單？

_tool_rewrite_todo_list 的回傳值只有 kept_items / new_items / total_items 幾個數字，清單內容不在工具結果裡。清單是 _get_system_hint 每一輪用 _format_todo_list 重新排版成 === CURRENT TASKS ===，接在歷史複本末尾送出；system prompt 只有使用規則，沒有清單。
