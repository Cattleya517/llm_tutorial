第 5 課 · 規劃：讓模型自己維護 TODO

agent_basic 讀書會 · 約 11 分鐘 · 對照檔案：agent.py 的 TodoItem、_tool_rewrite_todo_list、_tool_update_todo_status、_format_todo_list

這一課的收穫：能描述 TODO 清單的完整生命週期：system prompt 叫模型建 → 模型呼叫 rewrite_todo_list → 存在 self.todo_list → 每輪經由 hint 回到模型眼前 → update_todo_status 改狀態 → reset 清掉。

規劃不是程式寫的，是模型寫的

先打破一個直覺：agent.py 裡沒有任何一行程式會「規劃」。沒有任務拆解演算法、沒有依賴圖、沒有排程器。程式做的事只有兩件：

  1. 給模型一個可以寫計畫的地方（兩個工具 + 一個 list）。
  2. 每一輪把計畫再拿給模型看一次（system hint）。

Anthropic 的 context engineering 文章把這叫 structured note-taking：agent 把進度寫到 context 之外的地方（檔案、清單），之後再拉回 context，就算對話很長也不會忘記自己做到哪 [1]。self.todo_list 就是這份筆記；它不在 conversation_history 裡，但每輪都會被「唸」給模型聽。

規則：寫在 system prompt 裡

⌘F 搜 TODO List Management Rules（在 _init_system_prompt，約第 147 行）。模型怎麼用 TODO 完全由這幾句話決定：

  • 任務有 3 個以上步驟 → 立刻用 rewrite_todo_list 建清單。
  • 開始做某項 → 用 update_todo_status 改成 in_progress；同時只能有一項 in_progress。
  • 做完馬上標 completed。
  • 遇到錯誤或換方法 → 把相關項目標 cancelled，再加新的。

這些是「建議」，不是程式強制的。程式沒有檢查「只能一項 in_progress」，模型若不守規矩也不會報錯。改這段文字，模型的規劃行為就跟著改。

資料：TodoStatus 與 TodoItem

搜 class TodoStatus（約第 46 行）。四個狀態是一個 Enum：pending、in_progress、completed、cancelled。接著 class TodoItem(BaseModel)：

class TodoItem(BaseModel):
    id: int
    content: str
    status: TodoStatus = TodoStatus.PENDING
    created_at: str = Field(default_factory=lambda: datetime.now().isoformat())
    updated_at: Optional[str] = None

    @field_validator("content")
    @classmethod
    def content_must_be_meaningful(cls, v: str) -> str:
        v = v.strip()                                   # 模型偶爾送 "" 或 "   "
        if not v:
            raise ValueError("todo content must not be empty")
        return v

標起來的 validator 值得停一下。模型送來的字串是跨信任邊界的輸入：它可能是空白、可能是純空格。pydantic 在建構 TodoItem 時跑這個函式，不合格就丟 ValueError。這個例外一路往上，被 _execute_tool 的 except Exception 接住，包成 {"error": ...} 當工具結果回給模型（第 4 課的詳細錯誤）。模型下一輪會看到「todo content must not be empty」，自己改正。這是「在跟模型的邊界做驗證，錯誤交給模型處理」的最小範例 [2]。

兩個工具：契約與實作

跟第 2 課一樣，契約在 _get_tools_description（搜 "name": "rewrite_todo_list"，約第 386 行），實作在 _tool_rewrite_todo_list 與 _tool_update_todo_status（約第 745、773 行），由 _execute_tool 用名字 dispatch。

rewrite_todo_list(items: List[str])

def _tool_rewrite_todo_list(self, items: List[str]) -> Dict[str, Any]:
    kept_items = [item for item in self.todo_list
                  if item.status in [TodoStatus.COMPLETED, TodoStatus.CANCELLED]]
    new_items = []
    for content in items:
        new_items.append(TodoItem(id=self.next_todo_id, content=content,
                                  status=TodoStatus.PENDING))
        self.next_todo_id += 1                          # id 只增不減，不會重用
    self.todo_list = kept_items + new_items
    return {"success": True, "kept_items": len(kept_items),
            "new_items": len(new_items), "total_items": len(self.todo_list)}

名字叫 rewrite，但不是整份覆蓋：已完成、已取消的留著（當作歷史紀錄），只有 pending / in_progress 會被新的取代。所以模型「換方法」時，重寫一次就等於丟掉舊計畫、保留戰績。

update_todo_status(updates: List[{id, status}])

吃一個 list，每個元素是 {"id": 2, "status": "completed"}。實作就是對 self.todo_list 線性找 id、改 status、填 updated_at。找不到的 id 會被靜靜跳過，回傳的 updated_items 會比較少。契約那邊用 JSON Schema 的 enum 限制 status 只能是四個字串之一；實作用 TodoStatus(update["status"]) 再轉一次，字串不合法會丟 ValueError，同樣回給模型。

清單怎麼回到模型眼前

這是整課最重要的一條線，三個函式接力：

函式做什麼
_format_todo_list（約第 252 行）把 self.todo_list 轉成文字，每項 [id] emoji content (status)
_get_system_hint（約第 270 行）若 enable_todo_list 且清單非空，加一段 === CURRENT TASKS === 在系統狀態後面
execute_task 內 messages_to_send（約第 828 行）第 4 課的機制：hint 接在歷史複本末尾當一條 role: user，不存進歷史

模型在每一輪的最後一條訊息會看到類似這樣的東西：

=== SYSTEM STATE ===
Current Time: 2026-10-19 14:02:11
Current Directory: /Users/adamw/tutorials/llm_tutorial/agent_basic
...

=== CURRENT TASKS ===
TODO List:
  [1] ✅ 建立 notes/ 資料夾 (completed)
  [2] 🔄 在 notes/ 寫入 hello.txt (in_progress)
  [3] ⏳ 列出 notes/ 內容 (pending)

關鍵：模型不是靠記憶知道做到第幾項。就算歷史裡有二十輪前它呼叫 update_todo_status 的紀錄，真正讓它每輪都「看到當前狀態」的是這段每次重新產生的 hint。清單是程式的狀態（self.todo_list），文字只是每輪的投影。

一行補充：_save_trajectory 用 item.model_dump(mode="json") 輸出 TODO。mode="json" 讓 TodoStatus.COMPLETED 變成字串 "completed"，否則 Enum 物件進 json.dump 會出錯 [2]。

最後一站：reset

搜 def reset（約第 995 行）：self.todo_list = []、self.next_todo_id = 1。REPL 模式打 reset 才會清；單純跑完一個 execute_task 不會清，所以同一個 agent 連續接兩個任務，第二個任務會看到上一個任務的 completed 項目還在 hint 裡。

這些可以先跳過

  • created_at / updated_at：時間戳只進 trajectory.json，模型看不到。
  • execute_task 回傳 dict 裡手寫的 todo 轉換（約第 982 行）：跟 model_dump(mode="json") 等價。
  • _format_todo_list 裡的 emoji 對照表：純顯示。

預測一下

選一個答案，立刻看解釋。目的是檢查你有沒有把生命週期讀進去，不是考試。

清單目前有三項：[1] completed、[2] pending、[3] pending。模型呼叫 rewrite_todo_list 送來兩個新字串。呼叫後清單有幾項？

completed / cancelled 的保留（[1]），pending / in_progress 的全部丟掉（[2][3]），再加兩個新的 [4][5]。結果 1 + 2 = 3 項。注意 id 從 next_todo_id 接著編，不會回收 2 和 3。

模型呼叫 rewrite_todo_list，其中一個 item 是空字串 ""。接下來會怎樣？

TodoItem(content="") 觸發 content_must_be_meaningful，丟 ValueError。_execute_tool 的 except Exception 接住，包成 {"error": ...} 當工具結果回給模型。因為例外發生在 self.todo_list = kept_items + new_items 之前，清單保持原樣（只有 next_todo_id 可能已為前面合法的項目先加過）。

第 12 輪時，模型怎麼知道 [2] 現在是 in_progress？

_get_system_hint 每一輪重新讀 self.todo_list 產生 === CURRENT TASKS ===，接在歷史複本末尾送出。歷史裡只有它「呼叫過 update_todo_status」的紀錄和工具回傳的 updated_items 數字，沒有完整清單；hint 本身也不存進歷史（第 4 課）。
