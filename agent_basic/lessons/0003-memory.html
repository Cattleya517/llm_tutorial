第 3 課 · 記憶就是一個 list

agent_basic 讀書會 · 約 11 分鐘 · 對照檔案：01_loop.py 的 messages → agent.py 的 self.conversation_history、_init_system_prompt、reset、__main__

這一課的收穫：讀完後你能指出 conversation_history 從出生（只有一條 system prompt）到每一輪長出 user / assistant / tool 訊息的全過程，並解釋為什麼在 REPL 裡問第二個任務時，agent 會記得第一個。

先講結論

agent.py 沒有資料庫、沒有向量檢索、沒有任何「記憶模組」。所謂記憶就是 self.conversation_history，一個普通的 Python list，裡面放 dict。它只會變長（execute_task 只做 append），唯一會把它清掉的是 reset()。每一輪問模型，整份 list 都會送出去。第 1 課的 01_loop.py 用 messages 做的事，這裡一模一樣，只是多了名字和一些包裝。

第 0 條：system prompt（_init_system_prompt）

在 VSCode 搜 def __init__（約第 101 行）。往下幾行會看到 self.conversation_history = []，緊接著呼叫 self._init_system_prompt()（約第 141 行）。這個函式把一段長字串包成 list 裡的第一條訊息：

self.conversation_history = [
    {"role": "system", "content": system_content}
]

所以 agent 一出生，記憶裡就有且只有一條 role: "system"。這段 prompt 不用全文讀，它在要求模型四件事：

  • 複雜任務（3 步以上）先用 rewrite_todo_list 建 TODO，做一項標一項，一次只能有一項 in_progress（第 5 課）。
  • 注意訊息前面的時間戳，用它理解事件先後。
  • 注意 Tool call #n 計數，數字變大代表在鬼打牆，要換策略（第 4 課）。
  • 做完要寫 FINAL ANSWER: 再接總結（第 6 課；現在真正的結束條件是「沒有 tool_calls」）。

注意這段只寫規則和行為原則，不寫「現在幾點、在哪個目錄」這種每輪會變的東西。Anthropic 的 context engineering 文章把這叫做 system prompt 的「right altitude」：太低變成一堆 if-else 式的硬規則，太高又模糊到沒指引；該放的是穩定不變的工作方式 [1]。會變的狀態走另一條路（system hint，第 4 課）。

message.model_dump() 是把 OpenAI SDK 回傳的 pydantic 物件轉成 dict，這樣它才能和其他手寫的 dict 一起放進同一個 list、下一輪一起送出去。一次「模型叫工具」的迭代會在 list 尾巴長出三條，簡化後長這樣：

{"role": "user",      "content": "[2026-10-19 10:00:05] 01_loop.py 有幾行？"}
{"role": "assistant", "content": null,
                      "tool_calls": [{"id": "call_abc", "type": "function",
                                      "function": {"name": "execute_command",
                                                   "arguments": "{\"command\": \"wc -l 01_loop.py\"}"}}]}
{"role": "tool",      "tool_call_id": "call_abc",
                      "content": "[2026-10-19 10:00:10] [Tool call #1] {\"stdout\": \"60 01_loop.py\", ...}"}

實際 dump 出來的 assistant dict 還有 refusal、annotations、reasoning 等幾個多半是 null 的欄位，那是 SDK 的完整結構，看到不要驚訝。

模型下一輪再叫一次工具，就再長出 assistant + tool 兩條；最後一輪模型不叫工具、直接講話，長出一條 assistant 就結束。這個 role 的交替順序是 API 規定的：每條 tool 都要接在一條帶 tool_calls 的 assistant 後面 [2]。

只 append，不刪 → 多輪記憶免費送

再看一次 execute_task：它對 conversation_history 做的操作只有 append，函式開頭沒有 = []，結尾也沒有 clear()。所以同一個 SystemHintAgent 物件連續呼叫兩次 execute_task，第二次的 user 訊息會直接接在第一次的完整對話後面；模型看到的是「上一個任務的全部過程 + 新問題」。這就是為什麼第二個任務可以說「剛才那個檔案」。

搜 def reset（約第 995 行）：它不是 clear()，而是重新呼叫 _init_system_prompt()，整個 list 換成一條新的 system prompt。順便也清掉 todo_list、tool_calls、tool_call_counts，那些屬於第 5、6 課。

再往下看 if __name__ == "__main__"（約第 1008 行）。不帶參數執行就進入 REPL：input("Task > ") 讀一行，打 reset 呼叫 agent.reset()，打 quit 離開，其他都丟給 execute_task。整個 REPL 共用同一個 agent，所以記憶自然跨任務。

代價：每一輪都送整份

搜 messages=messages_to_send（約第 835 行）。送給模型的不是「最新那幾條」而是整份歷史。模型本身沒有狀態，每次呼叫都從零讀起，所以 list 越長，每一輪的輸入 token 就越多：第 10 輪送的東西包含前 9 輪的所有 assistant 和 tool 訊息。即使模型每輪只叫一個工具，成本仍一輪比一輪高，而且 tool 訊息的 content 常常是整個檔案或指令輸出，長得最快。

Anthropic 的說法是 context 是有限資源，每多塞一個 token 都會稀釋模型的注意力，長對話還會碰到 context window 上限 [1]。他們列的對策（compaction、把工具結果精簡、把進度寫成筆記）agent.py 一個都沒做：沒有截斷、沒有摘要，01_loop.py 至少還有 result[:4000]。這是它缺的保護，第 6 課再談。

兩個先知道就好的細節

複本與 hint：約第 826 行的 messages_to_send = self.conversation_history.copy() 之後 append 的那條 system hint 只存在於複本，不會進 conversation_history，所以歷史裡不會累積一堆狀態摘要；完整說明在第 4 課。

trajectory.json：搜 def _save_trajectory（約第 216 行），裡面的 "conversation_history": self.conversation_history 就是把這個 list 原封不動 dump 成 JSON。想看記憶長什麼樣，開這個檔就好；它每一輪都會覆寫，所以只反映最近一次執行。第 6 課會把它當回溯工具來用。

預測一下

選一個答案，立刻看解釋。目的是檢查你有沒有把「只 append、整份送、reset 才清」讀進去，不是考試。

在 REPL 打 reset 之後，conversation_history 裡剩什麼？

reset() 呼叫 _init_system_prompt()，它把 list 整個換成 [{"role": "system", ...}]。所以不是空 list，而是回到出生狀態：一條 system prompt。

REPL 裡第二個任務說「剛才那個檔案」，agent 為什麼知道是哪個？

模型本身沒有狀態，每次呼叫都只看送進來的 messages。第二次 execute_task 只是把新的 user 訊息 append 到舊歷史後面，整份一起送出去，模型才「看到」上一個任務讀過哪個檔。

模型每一輪都只叫一個工具。從第 2 輪到第 10 輪，每輪送給模型的輸入 token 會怎樣？

messages=messages_to_send 送的是整份歷史的複本。每輪至少多兩條（assistant + tool），而且 tool 的 content 沒有截斷，所以輸入 token 單調遞增。這就是「context 是有限資源」的實際成本。

主要來源

讀 Anthropic — Effective Context Engineering for AI Agents，「system prompt 的高度」和「context 是有限資源」兩段對應這一課的兩個重點。訊息格式與 role 順序以 OpenRouter — Tool & Function Calling 為準。
