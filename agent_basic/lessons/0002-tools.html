第 2 課 · 工具：契約與實作是兩個地方

agent_basic 讀書會 · 約 14 分鐘 · 對照檔案：01_loop.py 的 TOOLS / run_tool → agent.py 的 _get_tools_description、_execute_tool、_tool_execute_command

這一課的收穫：讀完後看到 agent.py 的任何一個工具，你能找到它的 JSON Schema（模型看到的那份）和它的 Python 實作（真正跑的那份），並說出兩者是靠「工具名字」和「參數名」對上的，中間沒有任何魔法。

先回想第 1 課：模型只會「說」，不會「做」

模型回覆裡的 tool_calls 只是一段 JSON：「我要叫 execute_command，參數是 {"command": "ls"}」。它沒有辦法碰你的硬碟。所以一個工具一定拆成兩份：

  1. 契約：用 JSON Schema 告訴模型「有這個工具、吃哪些參數」。送進 API 的 tools= 參數就是它。
  2. 實作：模型點名之後，真正跑 subprocess、開檔案的 Python 函式。

在 01_loop.py 裡這兩份分別叫 TOOLS 和 run_tool，相隔十幾行。在 agent.py 裡同樣是兩個地方，只是各自長了十倍。

契約：_get_tools_description

⌘F 搜 def _get_tools_description（約第 291 行）。它回傳一個 list，裡面是 6 個工具的 schema：前 4 個固定（read_file、write_file、code_interpreter、execute_command），後 2 個 TODO 工具只在 config.enable_todo_list 打開時 extend 進去。這個 list 在 execute_task 裡每一輪都以 tools=self._get_tools_description() 送給模型。

拿 execute_command 那一塊來看（節錄）：

{
    "type": "function",
    "function": {
        "name": "execute_command",
        "description": "Execute a shell command in the current directory",
        "parameters": {
            "type": "object",
            "properties": {
                "command":     {"type": "string", "description": "Shell command to execute"},
                "working_dir": {"type": "string", "description": "Optional working directory ..."}
            },
            "required": ["command"]
        }
    }
}

三件事值得停下來講：

  • 模型看到的只有這份。它看不到 _tool_execute_command 的任何一行 Python，不知道有 30 秒 timeout、不知道 cd 會被特別處理。模型「以為」工具會做什麼，完全來自 description 和每個參數的 description。
  • required 決定模型一定會給哪些參數。working_dir 不在裡面，所以模型多半省略它；對應的 Python 參數就必須有預設值（後面會看到 working_dir: Optional[str] = None）。
  • 這就是 Anthropic 所說的 ACI（agent-computer interface）。他們建議把工具描述當成給新同事看的 docstring 來寫：參數名要直白、example 要給、容易搞錯的邊界要寫出來，因為模型只能靠這些字決定怎麼用 [1]。agent.py 的 begin_line 描述特別寫了「1-based indexing. E.g., begin_line=10 starts from line 10」就是這個精神。

實作：_execute_tool 的 dispatch

搜 def _execute_tool（約第 439 行）。去掉計時與錯誤處理後，核心只有這樣：

def _execute_tool(self, tool_name, arguments):
    try:
        if tool_name == "read_file":
            result = self._tool_read_file(**arguments)
        elif tool_name == "write_file":
            result = self._tool_write_file(**arguments)
        elif tool_name == "code_interpreter":
            result = self._tool_code_interpreter(**arguments)
        elif tool_name == "execute_command":
            result = self._tool_execute_command(**arguments)
        elif tool_name == "rewrite_todo_list": ...
        elif tool_name == "update_todo_status": ...
        else:
            return {"error": f"Unknown tool: {tool_name}"}, error, None
        return result, None, duration_ms
    except Exception as e:
        return {"error": error_detail}, error_detail, duration_ms

兩份要「對上」的地方就在這裡，而且有兩層：

  1. 工具名字：schema 的 "name": "execute_command" ↔ if tool_name == "execute_command"。純字串比對，打錯一個字母就掉進 else: Unknown tool。
  2. 參數名字：**arguments 把模型送來的 dict 攤成關鍵字引數，所以 schema 的 properties 鍵名（command、working_dir）必須一字不差等於 def _tool_execute_command(self, command, working_dir=None) 的參數名。多一個模型自創的鍵、或 schema 改名而 Python 沒改，** 就會丟 TypeError。

注意回傳值是一個三元組 (result, error, duration_ms)，而且任何例外都被接住，變成 {"error": ...} 回去。這是刻意的：工具失敗不該讓整個迴圈掛掉，而是讓模型看到錯誤、自己換招。第 4 課會講 error_detail 裡附的「建議」是怎麼生出來的。

精讀一個實作：_tool_execute_command

搜 def _tool_execute_command（約第 691 行）。四個工具裡挑它，是因為它最常被叫到，也最能看出「實作裡有模型不知道的事」。

def _tool_execute_command(self, command: str, working_dir: Optional[str] = None):
    try:
        if working_dir is None:                         # 1. cwd：沒給就用 agent 記住的目前目錄
            working_dir = self.current_directory
        elif not os.path.isabs(working_dir):
            working_dir = os.path.join(self.current_directory, working_dir)

        stripped = command.strip()                      # 2. 攔截「純」cd
        if stripped.startswith('cd ') and not any(t in stripped for t in ('&&', ';', '|')):
            new_dir = ...
            if os.path.isdir(new_dir):
                self.current_directory = os.path.abspath(new_dir)
                return {"success": True, "command": command,
                        "output": f"Changed directory to: {self.current_directory}", "return_code": 0}
            else:
                raise FileNotFoundError(f"Directory not found: {new_dir}")

        result = subprocess.run(command, shell=True, capture_output=True,
                                text=True, cwd=working_dir, timeout=30)   # 3. 其他全部丟給 shell

        return {                                        # 4. 回傳固定形狀的 dict
            "success": result.returncode == 0,
            "command": command,
            "output": result.stdout,
            "error": result.stderr if result.stderr else None,
            "return_code": result.returncode,
            "working_dir": working_dir
        }
    except subprocess.TimeoutExpired:
        raise TimeoutError(f"Command timed out after 30 seconds: {command}")

為什麼要攔 cd？

每次 subprocess.run 都是一個新的 shell，跑完就消失。模型若先叫 cd src 再叫 ls，第二次的 shell 根本不記得第一次 cd 過。所以 agent 自己用 self.current_directory 記住「現在在哪」，純 cd 不交給 shell，而是改這個屬性；之後每次 subprocess.run(cwd=working_dir) 都從這裡出發。read_file、write_file 的相對路徑也都接到 self.current_directory，所以這一個屬性就是整個 agent 的「目前目錄」。

注意判斷條件：只有不含 &&、;、| 的 cd 才攔。cd proj && make 會直接掉到下面的 subprocess.run，make 會在 proj 裡跑，但 self.current_directory 不會變。程式註解有寫原因：若硬攔，會把 proj && make 整串當成目錄名。

回傳 dict 的形狀是給模型看的

execute_task 會把這個 dict json.dumps 後當 role: "tool" 訊息送回去。所以 success、output、error、return_code 這幾個鍵名其實是「工具結果的契約」，模型看到 "success": false 和非零的 return_code 就知道要換做法。

shell=True 加上任何字串都可以跑，表示這個工具沒有 sandbox：模型叫 rm -rf 它就 rm -rf。timeout=30 只防「跑太久」，不防「做壞事」。詳細在第 6 課。

另外三個工具：掃過就好

工具Python 參數（= schema 的 properties）實作重點
_tool_read_file（約 525）file_path, begin_line=None, number_lines=None相對路徑接 current_directory；先讀 1024 bytes 判斷是不是 binary；給了 begin_line 就只回那一段，並附 total_lines、partial_read: True，讓模型知道還有沒讀完的部分。
_tool_write_file（約 639）file_path, contentos.makedirs(..., exist_ok=True) 自動建目錄，然後整個覆寫。回 bytes_written、lines_written。
_tool_code_interpreter（約 661）codeschema 說「restricted environment」，實作其實就是 exec(code, exec_ns) 加 redirect_stdout 抓輸出。沒有任何限制，描述跟實作不一致是這份程式的已知落差。

剩下兩個 _tool_rewrite_todo_list、_tool_update_todo_status 的 dispatch 跟上面一樣，但它們改的是 agent 自己的狀態而不是外部世界，留到第 5 課。

回到 execute_task：參數是怎麼進來的

搜 raw_args = tool_call.function.arguments（約第 873 行）。模型送來的參數不是 dict，是一段 JSON 字串，得先 json.loads。agent.py 比 01_loop.py 多了一個保護：

raw_args = tool_call.function.arguments or "{}"
try:
    function_args = json.loads(raw_args)
except json.JSONDecodeError as exc:
    err = f"Invalid tool arguments (not valid JSON): {exc}. Raw arguments: {raw_args[:500]}"
    self.conversation_history.append({"role": "tool", "tool_call_id": tool_call.id,
                                      "content": json.dumps({"error": err})})
    continue

result, error, duration_ms = self._execute_tool(function_name, function_args)

模型偶爾會吐出壞掉的 JSON（截斷、多一個逗號）。01_loop.py 會在 json.loads 直接炸掉；agent.py 則把錯誤當成工具結果送回去，continue 到下一個 tool_call，迴圈繼續。和 _execute_tool 的 except Exception 是同一個哲學：壞事發生時，回報給模型，不要中斷。

進階一句話：「兩個地方要對上」這件事其實可以消掉。把每個工具的參數寫成一個 pydantic BaseModel，Model.model_json_schema() 就能直接產出 parameters 那一段，實作再吃同一個 model，名字就只在一處出現。agent.py 已經在 TODO 用了 pydantic，但工具契約仍是手寫；這一課不實作，只記得有這條路。語法見 pydantic — Models。

這些可以先跳過

  • _get_detailed_error / _get_error_suggestions 的內容：只是把 exception 字串比對幾個關鍵字，附上「檢查路徑」之類的建議。知道它們在 _execute_tool 的 except 裡被呼叫就夠，第 4 課再看。
  • _tool_read_file 裡的 codecs.getincrementaldecoder：處理 1024 bytes 邊界切到半個中文字的細節。
  • start_time / duration_ms 計時：只進 ToolCall 紀錄和 trajectory，不影響模型看到的東西。
  • _tool_code_interpreter 註解裡關於 exec namespace 的說明：Python 作用域的小坑，跟 agent 無關。

預測一下

選一個答案，立刻看解釋。檢查的是「名字對上」和「錯誤回給模型」這兩條有沒有讀進去。

把 schema 裡 execute_command 的參數 command 改名成 cmd，但 _tool_execute_command(self, command, ...) 沒改。模型照新 schema 送出 {"cmd": "ls"}，接下來會怎樣？

self._tool_execute_command(**{"cmd": "ls"}) 會丟 TypeError: unexpected keyword argument 'cmd'，但它發生在 _execute_tool 的 try 裡，被 except Exception 接住，變成 {"error": "Tool 'execute_command' failed with TypeError: ..."} 當 role: "tool" 送回去。模型可能反覆重試同一個錯誤，直到放棄或用完 max_iterations；過程中不會崩潰，工具也跑不起來。

模型決定要不要用 code_interpreter、怎麼用的時候，它對這個工具的 Python 實作知道多少？

送進 API 的只有 _get_tools_description 回傳的 schema：name、description、parameters。模型看不到 exec(code, exec_ns)，所以它會相信描述裡的「restricted environment」。這就是為什麼 Anthropic 說工具描述要當成給人看的文件來寫：那是模型唯一的資訊來源。

目前 self.current_directory 是 /work，模型叫 execute_command 跑 cd proj && make。執行完之後呢？

字串含 &&，所以不符合「純 cd」的攔截條件，整串交給 subprocess.run(..., shell=True, cwd="/work")。shell 會在 proj 裡跑 make，但那個 shell 結束就沒了，self.current_directory 仍是 /work。只有單獨的 cd proj 才會改到屬性。

主要來源

工具契約與 tool_calls 的格式看 OpenRouter — Tool & Function Calling，它的 tools 範例和 _get_tools_description 的結構一模一樣。「描述要寫給模型看得懂」的設計原則看 Anthropic — Building Effective Agents 附錄 2「Prompt engineering your tools」。
