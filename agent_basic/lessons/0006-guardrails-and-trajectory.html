第 6 課 · 保護措施與軌跡：agent 哪裡會失控、怎麼回放

agent_basic 讀書會 · 約 12 分鐘 · 對照檔案：agent.py 的 execute_task、_tool_execute_command、_save_trajectory，以及跑完任務後出現的 trajectory.json

這一課的收穫：讀完後你能列出這份 agent 已有的四道保險和缺的三道，各自指到程式碼的哪一行；並且能打開 trajectory.json，把一次任務從頭回放一遍。

為什麼 agent 需要保險

前五課講的是 agent 怎麼「做對」；這一課講它怎麼「做壞」。一個會自己呼叫工具的迴圈，失控的方式很固定：跑不停（一直叫工具不給答案）、卡住（某個工具永遠不回來）、模型講錯話（回了格式不對的東西）、外部炸掉（API 錯誤、網路斷線）。Anthropic 的建議很樸素：給 agent 明確的停止條件（stopping conditions），並在每一步都拿「ground truth」——工具的真實結果——來校正，而不是讓模型一路自說自話 [1]。下面逐一對到程式碼。

A · 已有的四道保險

在 VSCode 用 ⌘F 搜 def execute_task（約第 794 行），四道保險有三道在這個函式裡。

防什麼程式碼在哪怎麼防
跑不停execute_task 的 while iteration < max_iterations（約 816 行，預設 20）；以及同函式的空回覆分支（約 860 行）模型一直叫工具不給答案，最多 20 輪就出去。另一種「跑不停」是模型回了空字串又沒 tool_calls：舊版會把它再送回去燒完剩下的輪數，現在直接 logger.warning(...) 後 break。
卡住_tool_execute_command 裡 subprocess.run(..., shell=True, timeout=30)（約 723–729 行）指令 30 秒沒回來就丟 subprocess.TimeoutExpired，函式把它改包成 TimeoutError 往上丟；_execute_tool 接住、變成 error 字串回給模型，而不是整個程式掛掉。
模型講錯話execute_task 裡的 except json.JSONDecodeError（約 876–895 行）模型給的 tool arguments 不是合法 JSON 時，不 crash：記一筆 ToolCall(arguments={}, error=...)，再 append 一條 role: "tool" 的錯誤訊息回歷史，continue 讓模型自己改。
外部炸掉execute_task 最外層的 except Exception as e（約 963 行）；__main__ 的 run()（約 1015 行）API 呼叫失敗、模型名不存在、網路斷線…都走這裡：先 _save_trajectory(iteration)，再回傳 {"error": str(e), "final_answer": None, "success": False, ...}。run() 看到 result.get("error") 就印 === ERROR ===。

注意第二、三道的共同精神：工具層的失敗變成「給模型看的訊息」，迴圈不斷。模型看到 TimeoutError 或 Invalid tool arguments 之後，通常會換個做法再試。這就是 [1] 說的「用 ground truth 校正」——錯誤本身也是 ground truth。

正常結束則走 execute_task 最後的 return（約 979 行）："success": final_answer is not None，所以 20 輪跑完還沒答案時，success 會是 False 但沒有 error。

B · 缺的三道保險

這份 agent 是教學用的，有三件生產環境一定會做的事它沒做。這裡只點出證據，不實作（MISSION 說好的）。

缺什麼證據為什麼要在意
工具結果不截斷execute_task 裡 tool_content = json.dumps(result)（約 934 行）整包 append 進歷史。對照 01_loop.py 最後一行有 result[:4000]。模型 read_file 一個 5 MB 的檔，整份進 context，之後每一輪都要重送。Anthropic 的 context engineering 文章把「工具結果要省 token」列為第一件事 [2]。
沒有 sandbox_tool_execute_command 的 shell=True（約 725 行）；_tool_code_interpreter 的 exec(code, exec_ns)（約 677 行）。docstring 寫 "restricted environment"，但 exec_ns = {} 只是乾淨的命名空間，import os; os.system(...) 照跑。模型想到什麼就執行什麼，權限等於你自己。不要拿它跑來路不明的任務；讀書會示範時在一個可以丟掉的目錄裡跑。
不追蹤 token / 費用全檔搜 response.usage 或 .usage：零筆。模型回應裡的 token 數從來沒被讀過。跑不停的保險只擋「輪數」，不擋「每輪多貴」。20 輪 × 越來越長的歷史，帳單是二次方成長的。

C · 觀測：它怎麼記錄自己做過什麼

每一次工具呼叫一筆 ToolCall

⌘F 搜 class ToolCall（約第 72 行）。一個 pydantic 模型，欄位是 tool_name、arguments、result / error（二擇一）、call_number（第幾次叫同一個工具）、timestamp、duration_ms。在 execute_task 裡每執行完一個工具就 self.tool_calls.append(ToolCall(...))（約 920 行）；JSON 壞掉那條分支也會記一筆，只是 arguments={}。

_save_trajectory：每一輪 dump 一次

搜 def _save_trajectory（約第 216 行）。它在 execute_task 被叫的時機：每輪開頭、結束時（找到答案，或 20 輪用完走到迴圈後面的 return）、出錯時（最外層 except）。每次都用 'w' 模式覆寫 trajectory.json，所以檔案永遠是「最新狀態」，不是歷史累積。重要的 key：

key內容
conversation_history第 3 課的那個 list：system prompt、user、assistant（含 tool_calls）、tool 結果。
last_llm_messages最後一輪真正送給模型的 messages。跟上面一項的差別就是第 4 課的 system hint——那條臨時加在末尾、沒存進歷史的 role: "user" 狀態摘要。兩個欄位並排比，hint 的「臨時加上、不存檔」一眼就看出來。
tool_calls[call.model_dump() for call in self.tool_calls]，上面那些 ToolCall。
todo_list第 5 課的 TODO，model_dump(mode="json")。
final_answer還沒答完時是 null。
config哪些 hint 開著，方便事後對照「模型當時看到了什麼」。

開關在 SystemHintConfig（約第 83 行）：save_trajectory: bool = True、trajectory_file: str = "trajectory.json"。關掉它 _save_trajectory 第一行就 return。

終端機的 log

檔案開頭（約 40–43 行）：logging.basicConfig(level=logging.INFO, format='%(message)s')，所以 log 不帶時間與模組名，乾淨得像 print；接著把 httpx 和 openai 兩個 logger 壓到 WARNING，否則 SDK 每個 HTTP request 都會印一行。跑任務時你看到的 ── iteration n/20 ──、🔧 工具名 (call #n)、✅ 結果前 150 字、❌ 錯誤前 150 字 全在 execute_task 裡。

所以觀測有兩層：log 看現場（即時、只有摘要），trajectory.json 看全貌（事後、一字不漏）。debug 的時候先看 log 找到哪一輪出事，再開 JSON 看那一輪模型到底收到什麼。

這些可以先跳過

  • _reasoning_safe_temperature：某些 reasoning 模型只吃 temperature=1 的相容補丁。
  • "FINAL ANSWER:" in content 的字串切割（兩處）：舊版的結束訊號；現在「沒有 tool_calls」才是真正的停止條件，這幾行只是向下相容。
  • _tool_rewrite_todo_list 裡的 kept_items / new_items：第 5 課講過的「完成項保留」，跟保護無關。

預測一下

選一個答案，立刻看解釋。目的是檢查你能不能從程式碼預測 agent 的行為，不是考試。

模型呼叫 execute_command，指令是 sleep 60。接下來會怎樣？

subprocess.run(timeout=30) 在 30 秒時丟 TimeoutExpired，_tool_execute_command 改包成 TimeoutError("Command timed out after 30 seconds: sleep 60")；_execute_tool 的 except 接住，變成 {"error": ...} 當工具結果回給模型，迴圈繼續。終端機會印一行 ❌。

模型回了一個 tool call，但 arguments 是 {"command": ls}（字串沒加引號，不是合法 JSON）。接下來會怎樣？

json.loads(raw_args) 丟 JSONDecodeError，被 execute_task 裡專門的 except 接住：記一筆 ToolCall(arguments={}, error=...)，append 一條 role: "tool" 內容是 {"error": "Invalid tool arguments (not valid JSON): ..."}，然後 continue。下一輪模型看到這條，通常會重發一次正確的 JSON。沒有任何自動修正。

你想知道「最後一輪模型到底收到了哪些 messages」（包含那條臨時的 system hint）。該看哪裡？

要看 trajectory.json 的 last_llm_messages。它存的是 messages_to_send——歷史的複本加上 hint。conversation_history 沒有那條 hint（第 4 課：臨時加上、不存檔）；終端機的 log 只有摘要，不印 messages。

主要來源

Anthropic — Building Effective Agents：停止條件、每一步用環境回饋（ground truth）校正、agent 要能在哪裡暫停讓人檢查。Anthropic — Effective Context Engineering for AI Agents：工具結果要省 token、長任務要 compaction——正是這份 agent 缺的第一道保險的理由。
