每課用到的名詞以這份為準。依課次排序，同一課內按講解順序；「agent.py」欄以函式名為準，行號是 2026-10-19 的檔案，會漂（重取：grep -n "def " agent.py）。「避免」列的是同義詞——讀書會裡請統一用粗體那個。

第 1 課 · 迴圈

English中文定義agent.py課
agent代理（直接說 agent） 讓 LLM 在迴圈裡根據環境回饋決定下一步要用哪個工具的程式；模型只「說」要做什麼，動手的是 Python。 避免：AI 助理、bot、智能體 來源：Anthropic — Building Effective Agents（"LLMs using tools based on environmental feedback in a loop"） class Agent（約 96）1
workflow vs agent工作流 vs 代理 workflow 的步驟順序由程式碼寫死，agent 的下一步由模型在執行期決定；execute_task 不預設要呼叫哪些工具、呼叫幾次，所以是 agent。 避免：pipeline、chain（都指 workflow 那一邊） 來源：Anthropic — Building Effective Agents execute_task 的 while 迴圈（約 816）1
iteration / turn一輪 迴圈走一圈：送一次 messages_to_send 給模型、拿到一條回覆、執行它要求的所有工具。一輪可能有零個或多個 tool call。 避免：step、round（01_loop.py 的 step 就是這個） execute_task：iteration += 1，log 印 ── iteration n/20 ──1
max_iterations最大輪數 迴圈上限（預設 20），防模型一直叫工具永不收尾；是最便宜的保護措施。 execute_task(task, max_iterations=20)；while iteration < max_iterations1、6
messages / conversation history對話歷史 一個普通的 Python list，元素是帶 role 的 dict；每一輪整份送給模型，agent 的記憶就是它。 避免：chat log、context（context 是「這次實際送進模型的東西」，見第 3 課） 來源：OpenRouter — Tool & Function Calling self.conversation_history（__init__ 約 129；_init_system_prompt 放第 0 條）1、3
role（system / user / assistant / tool）訊息角色 每條訊息的身分標籤：system 是規則、user 是人（或 hint）、assistant 是模型回覆（可帶 tool_calls）、tool 是工具結果。tool 訊息必須緊接在帶 tool_calls 的 assistant 訊息之後。 來源：OpenRouter — Tool & Function Calling execute_task 裡三種 append：user 任務、message.model_dump()、{"role": "tool", ...}1
tool_calls工具呼叫清單 模型回覆裡的欄位，列出它這一輪想呼叫的函式名與 JSON 字串參數；為空就代表模型認為答完了，迴圈結束。 來源：OpenRouter — Tool & Function Calling execute_task：has_tool_calls = bool(getattr(message, "tool_calls", None))；for tool_call in message.tool_calls1
tool_call_id工具呼叫 ID 模型替每個 tool call 配的識別字；role: "tool" 的結果要帶同一個 id，API 才知道這是回答哪一次呼叫。 來源：OpenRouter — Tool & Function Calling execute_task："tool_call_id": tool_call.id1
OpenRouter / model id模型路由服務 / 模型代號 OpenRouter 是一個 OpenAI 相容的 API 閘道，用 "供應商/模型名" 形式的字串（如 moonshotai/kimi-k2.6）選模型；agent.py 只支援這一個 provider。 來源：OpenRouter 文件；支援 tools 的模型列表 openrouter.ai/models?supported_parameters=tools OPENROUTER_BASE_URL、DEFAULT_MODEL（約 35）；__init__ 讀 OPENROUTER_MODEL1
temperature溫度 採樣隨機度；agent 任務要穩定，這裡用 0.3（reasoning 模型只接受 1，由 _reasoning_safe_temperature 補丁）。 execute_task：temperature=_reasoning_safe_temperature(self.model, 0.3)；補丁在約 281
tool_choice工具選擇策略 告訴 API 模型「可不可以 / 必不必須」叫工具；"auto" 讓模型自己決定，所以「不叫工具」才能當結束訊號。 來源：OpenRouter — Tool & Function Calling（補充：OpenAI Function calling guide，名詞不同勿對照程式） execute_task：tool_choice="auto"1

第 2 課 · 工具

English中文定義agent.py課
dispatch派送 依 tool call 的函式名，把參數轉交給對應 Python 函式的那段 if / elif；名字必須跟工具契約一字不差。 避免：router、registry _execute_tool（約 439）→ _tool_*2
pydantic BaseModel / model_dump / model_json_schema資料模型 / 轉 dict / 產 schema BaseModel 是帶驗證的資料類別；model_dump() 把它變成普通 dict（mode="json" 時 Enum 轉成字串）；model_json_schema() 從同一個類別產出 JSON Schema。注意 message.model_dump() 是 OpenAI SDK 自己的 pydantic 物件轉 dict，跟本檔的 TodoItem、ToolCall 是兩回事。model_json_schema() 本檔未用——契約是手寫的，第 2 課只提「可以用它把契約和實作合一」。 來源：pydantic — Models TodoItem、ToolCall、AgentConfig（46–95）；_save_trajectory 的 item.model_dump(mode="json")；execute_task 的 message.model_dump()2、6
tool / function calling工具呼叫 API 層的機制：你用 tools 參數告訴模型有哪些函式，模型用 tool_calls 回答「請幫我呼叫這個」，真正執行永遠在你這邊。 避免：plugin、skill、action（都是產品名，不是協定名） 來源：OpenRouter — Tool & Function Calling execute_task：tools=self._get_tools_description()2
tool contract / JSON Schema工具契約 描述一個工具的名稱、用途說明、參數型別與必填欄位的 JSON Schema；模型只看得到這份描述，看不到 Python 實作。 避免：tool definition、tool spec（同義，統一叫契約） 來源：OpenRouter — Tool & Function Calling；描述怎麼寫才讓模型看得懂見 Anthropic — Building Effective Agents 的 ACI 一節 _get_tools_description（約 291，六個工具）2

第 3 課 · 記憶

English中文定義agent.py課
context window上下文視窗 模型一次請求能讀進的 token 上限；agent.py 每輪把整份 conversation_history 送進去，所以歷史只會越滾越大，直到撞到上限。 來源：Anthropic — Effective Context Engineering 沒有對應程式；看 execute_task 的 messages_to_send = self.conversation_history.copy()3
context engineering上下文工程 決定「每一輪到底送什麼進模型」的工程：system prompt 的高度、工具結果要不要瘦身、狀態摘要放哪裡。system hint、TODO 清單、詳細錯誤都是它的實例。 避免：prompt engineering（那是單一 prompt 的措辭，本 track 不講） 來源：Anthropic — Effective Context Engineering 整個 messages_to_send 的組裝（execute_task 約 826–830）3、4
compaction壓縮歷史 歷史快撞到 context window 時，把舊訊息摘要成一段短文、丟掉原文的做法。agent.py 沒有實作——歷史只會 append，最接近的是 reset() 整個清掉。 避免：summarization（太廣）、truncation（那是截單一工具結果） 來源：Anthropic — Effective Context Engineering 無；reset（約 995）是唯一清空點3、6
system prompt系統提示 歷史的第 0 條、role: "system"，放不隨任務變的規則：TODO 用法、看時間戳與計數、錯誤處理、FINAL ANSWER: 結束訊號。跨任務不重寫，reset() 才重建。 避免：instructions、persona 來源：Anthropic — Effective Context Engineering（system prompt 的「高度」） _init_system_prompt（約 141）3

第 4 課 · System hint

English中文定義agent.py課
system hint狀態欄 每一輪臨時接在歷史複本末尾、送完就丟的一條 role: "user" 訊息，內容是系統狀態（時間、cwd、OS）與目前 TODO。歧義說明：書裡「system hint」泛指五件事（對應 AgentConfig 的五個開關：時間戳、工具計數、TODO、詳細錯誤、系統狀態）；本檔 _get_system_hint 只產「狀態 + TODO」這一條是臨時的，時間戳與計數則是直接寫進歷史的（見下兩條）。本 track 說「system hint」時指書的廣義，說「_get_system_hint」時指那一條。 避免：status bar 直譯「狀態列」、system message（它的 role 是 user 不是 system） 來源：《深入理解 AI Agent》chapter2/system-hint README（為何用 role=user 注入在末尾） _get_system_hint（約 270）、_get_system_state（約 180）；注入點 execute_task 的 messages_to_send.append({"role": "user", "content": system_hint})4
timestamp時間戳 貼在 user 任務開頭和每條工具結果開頭的 [YYYY-MM-DD HH:MM:SS]，讓模型看得出事件先後與耗時；跟 hint 不同，它是存進歷史的。 _get_timestamp（約 204）；execute_task 的 timestamp_prefix 與 metadata_parts4
tool call counter工具呼叫計數 每個工具名各自累計被呼叫幾次，貼在工具結果開頭 [Tool call #n for 'name']，讓模型察覺自己在鬼打牆；同樣存進歷史。 self.tool_call_counts（__init__）；execute_task 裡 call_number4
detailed error詳細錯誤 工具拋例外時，不只回 str(e)，而是回「哪個工具、什麼參數、traceback、建議怎麼修」的整段文字，讓模型下一輪能自己改策略；由 config.enable_detailed_errors 開關。 _get_detailed_error（約 479）、_get_error_suggestions（約 498）；呼叫點在 _execute_tool 的 except4

TODO list / structured note-taking待辦清單 / 結構化筆記 模型用工具自己維護的一份計畫（TodoItem list），每輪經 system hint 回灌給它看；是 context engineering 裡「把狀態寫在 context 外面、再摘要回來」的 note-taking 做法。 避免：plan、scratchpad（太籠統） 來源：Anthropic — Effective Context Engineering（structured note-taking） TodoItem / TodoStatus（46–70）、_tool_rewrite_todo_list（約 745）、_tool_update_todo_status（約 773）、_format_todo_list（約 252）；規則寫在 _init_system_prompt5

第 6 課 · 保護與觀測

English中文定義agent.py課
FINAL ANSWER:結束訊號（舊） system prompt 要求模型答完時寫的字串標記；現在真正的結束條件是「沒有 tool_calls」，這個標記只用來切出最後答案。 _init_system_prompt 最後一段；execute_task 的 split("FINAL ANSWER:", 1)1、6
sandbox沙盒 把工具執行關進受限環境（容器、權限白名單、路徑限制），讓模型亂叫工具也傷不到主機。agent.py 沒有實作：execute_command 直接 subprocess.run(shell=True)、code_interpreter 直接 exec()，只有 timeout=30 一道防線。 避免：jail、容器化（是手段之一，不是概念本身） 無；風險點在 _tool_execute_command（shell=True 約 725、timeout=30 約 729）、_tool_code_interpreter（exec 約 677）6
trajectory軌跡 agent 一次任務從頭到尾的完整紀錄：歷史、每次送給模型的實際訊息、所有 tool call 與耗時、TODO；每輪覆寫到 trajectory.json，用來事後回溯。 避免：log（log 是 stdout 的摘要，trajectory 是完整狀態）、trace _save_trajectory（約 216）、ToolCall（約 72）、self.last_llm_messages；AgentConfig.trajectory_file6
truncation截斷工具結果 把過長的工具輸出切到固定長度再塞回歷史，避免一個 cat 大檔就吃光 context window。agent.py 沒有做——tool_content = json.dumps(result) 原樣進歷史；檔案裡的 [:150]、[:200] 只截 log 顯示，max_tokens=8192 是限模型輸出，都不是這件事。01_loop.py 的 result[:4000] 才是。 來源：Anthropic — Effective Context Engineering（工具結果要省 token） 無；應該加在 execute_task 的 tool_content = json.dumps(result) 之後。_tool_read_file 的 begin_line / number_lines 是讀取端的部分替代6
